\paragraph{Manual fault injection.} No mutation testing tool is assumed to be
available for GDScript, so once the tests are implemented the team will measure
test-suite strength by hand. A team member who did not write the code
introduces one small fault at a time in a separate branch and runs the full
suite. The faults target at least ten critical rules: the permission check
(FR-TEAM-7), the pairing-code retry limit (FR-DEV-4), the 30-day grace period
(FR-LRN-6), incomplete-session handling (SR-8), the hidden-item filter (SR-12),
the flash limit (SR-6), the export record count (SR-16), the low defaults
(SR-4), the invite-code expiry check (FR-TEAM-1), and the start-cue gate
(SR-5). The mutation score is the fraction of faults detected by at least one
failing test. Every surviving fault leads to a new or strengthened test.

\label{sec:impl-ver}

The implementation will be verified dynamically and statically.

\paragraph{Dynamic verification.} The system tests in Section 4 and the unit
tests in Section 5 are the primary evidence for functional and nonfunctional
requirements. Automated tests run in continuous integration on every pull
request (Section~\ref{sec:automated-tools}). Manual system tests are run by a team member
who did not implement the feature, before the Rev 0 demo and again before the
final demo.

\paragraph{Pull-request review.} Every pull request needs an approving review
from a member other than its author, following the rotation in
Section~\ref{sec:team}. The reviewer confirms that the change follows the
coding standard, uses static typing, includes or updates tests, contains no
credentials, and respects the relevant safety requirements. For example, no
audio or animation may start before the Learner's start cue (SR-5), and Learner
error messages must be calm and short (SR-7).

\paragraph{Code walkthroughs.} The team holds a 60-minute walkthrough for each
of these safety- or privacy-critical areas: access control and permissions,
pairing and invite codes with lockout, deletion and retention, offline queue
and synchronization, session recording, and data export. The author presents
the code, at least two other members inspect it against the requirements it
supports, and defects become issues. Areas that exist at Rev 0 are walked
through before the Rev 0 demo, and the rest before the final demo.

\paragraph{Static analysis.} Lint and format checks, strict typing warnings,
dependency scanning, and secret scanning run automatically
(Table~\ref{tab:tools}). A pull request cannot be merged while these checks
fail.

\paragraph{Inspection of Learner-facing assets.} Screen captures are recorded to count flashes in every one-second window to check
SR-6 (no more than three). The the default settings stored for each game are reviewed for low stimulation, volume, and celebration intensity (SR-4), and every task is checked so that it can be completed with touch or mouse input (SR-10).

\paragraph{Platform verification.} The manual platform matrix for
NFR-PORT-1 to NFR-PORT-3 is run on physical tablets owned by the team, and iOS and Android
simulators or emulators for older operating system versions, and Chrome,
Firefox, and Edge.

\paragraph{Out of scope.} The Godot engine and third-party libraries are
assumed to have been verified by their maintainers. The team tests only how
\progname{} uses them.

The team will use three automated tools for the Godot client, all of which run
from the command line so that they can be used locally and before a pull
request is merged. The commands are documented in the project
repository, and every team member runs them before submitting a pull request.
A change is ready to merge only when all tests pass, the linter reports no
errors, the formatter reports no differences, and Godot reports no warnings.

\paragraph{GUT (Godot Unit Test).} GUT is the unit testing framework for
GDScript. It is installed as an add-on in the project's \texttt{addons}
directory. Test scripts live in a \texttt{test} directory, extend
\texttt{GutTest}, and are named \texttt{test\_*.gd}. Each test function is
named \texttt{test\_<unit>\_<condition>\_<expected result>}, and a comment above
it gives the test ID from Sections 4 and 5 and the requirement ID it supports,
so that the traceability tables can be checked against the code. The team will use three GUT features in particular:
\begin{itemize}
  \item doubles and stubs replace the server connection, so that behaviour such
  as queuing results when the connection is lost (FR-DATA-8, SR-9) can be tested
  without a network;
  \item parameterized tests run the same check over several inputs, such as
  correct, incorrect, expired, and reused pairing and invite codes (FR-DEV-4,
  FR-TEAM-1); and
  \item signal watching confirms that game state changes, such as pausing,
  restarting, and aborting, emit the expected signals (FR-PLAY-5 to FR-PLAY-7).
\end{itemize}

\paragraph{gdlint and gdformat.} These two command-line tools come from
gdtoolkit, and the team will install the release that matches the Godot major
version used by the project. \texttt{gdlint} checks GDScript files against
naming, ordering, and design rules, with the team's chosen settings stored in a
\texttt{.gdlintrc} file in the repository. \texttt{gdformat} reformats files to a
single style. Team members run \texttt{gdformat} on the files they changed
before committing, and the pull-request check runs \texttt{gdformat --check}
and \texttt{gdlint} on the whole project. The check fails on any lint error or
any file that is not formatted. A consistent style keeps code reviews focused on
behaviour, and the lint rules catch problems such as unused or badly named
code before a reviewer has to.

\paragraph{GDScript warnings.} Godot's GDScript warnings are configured under
\emph{Project Settings} $\rightarrow$ \emph{Debug} $\rightarrow$
\emph{GDScript}, and the settings are saved in \texttt{project.godot}, so the
whole team shares them. Several useful warnings are ignored by default, so the
team enables them and turns on the option to treat warnings as errors. The
enabled warnings include untyped declarations, unsafe property access, unsafe
method access, unsafe casts, unused variables, shadowed variables, integer
division, and narrowing conversions. Together these make the team declare types
for variables and function signatures, which lets Godot find many type mistakes before the game runs.

\paragraph{Limits of these tools.} Passing these checks does not show that
\progname{} is correct. Lint, format, and warning checks find only style and
type problems, and GUT tests find only the faults they were written to detect.
The system tests in Section 4, the reviews and walkthroughs in
Section~\ref{sec:impl-ver}, and the fault-injection exercise in
Section~\ref{sec:plan-ver} supply the rest of the evidence.
